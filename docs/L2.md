# BONNIE L2 Specification — Discovery: the agent tree

**Status:** draft for `v0.2`, not built · **Audience:** implementing agent
**Read first:** [`SPEC.md`](SPEC.md) (especially §1 layers, §8 invariants)

This document specifies the layer that turns BONNIE from a library you wire
by hand into a framework you scaffold, edit, and build. It records what is
adopted from eve's authoring model, what is adapted for Go, and what is
refused on purpose.

---

## 1. What L2 is

L1 made a run durable. L3 made it reachable. L2 makes an agent **authored**:
a directory of files with meaning from their paths, which BONNIE discovers,
wires, and compiles.

```
authored tree          discovery                    one static binary
─────────────         ──────────                    ─────────────────
agent.yaml      ──┐    manifest  → run time    ┌→   serve --agent  (no build)
instructions.md │  ┌───────────────────────┤
skills/         ├──┤ codegen   → build time  │→   bonnie build → ./my-agent
workspace/      │  └───────────────────────┤
tools/*/tool.go ─┘         go build         ┘    the binary alone serves
```

The central fact, restated from the design discussion: **discovery is a
build-time idea in Go.** eve discovers at run time because Node loads
TypeScript on every start. Go compiles. So data resolves at run time, code
resolves at build time, and the binary is the product of discovery — not the
thing that rules it out.

### The one rule

**No run-time plugin loading.** No `.so` plugins, no reflection registries,
no embedded interpreter. Go's `plugin` package is platform-fragile and would
break the single-static-binary property. Code is wired by codegen; data is
wired by the manifest. Say this in every task that touches L2, or a
contributor will reach for `dlopen`.

---

## 2. The two kinds

| Kind | Examples | Resolves | Mechanism |
|---|---|---|---|
| **Data** | model, instructions, sandbox config, channel bindings, skills, workspace seed files, MCP connections | run time (`serve --agent`) or build time (`go:embed`) | the manifest and the loader |
| **Code** | custom tools, mutating hooks | build time only | codegen into `bonnie_gen.go` |

The split is the whole design. It answers "what is there to discover in a
compiled binary?": everything data-shaped is discovered when `serve` reads
the manifest or when `build` embeds it; everything code-shaped is discovered
when the generator walks the tree and the compiler type-checks the result.

## 3. The tree

```
my-agent/
├── agent.yaml            # the manifest (or agent.toml / agent.json)
├── instructions.md       # base system prompt
├── tools/                # optional Go tools, one directory per tool
│   └── charge_card/
│       └── tool.go       # func Tool() kit.Tool
├── skills/               # optional markdown; embedded, seeded into the sandbox
├── workspace/            # optional seed files, mirrored into /workspace
├── go.mod                # added by `bonnie init --tools` only
├── main.go               # added by `bonnie init --tools` only
└── bonnie_gen.go         # generated; safe to delete and regenerate
```

Decisions:

- **The agent root is the module root** (eve's flat layout). A BONNIE agent
  project is a Go module; library-mode hosts that embed the runner in a
  larger application use none of this, and stay first-class. The scaffold
  does not create a nested `agent/` directory, because `go:embed` patterns
  cannot cross package boundaries and the generated file must be able to
  reach the authored files.
- **Naming from paths** — adopted from eve: `tools/charge_card/` names the
  tool `charge_card`; the agent title comes from the manifest `title`, else
  the directory base name (eve: `package.json` name, else directory name —
  [getting-started](https://eve.dev/docs/getting-started)).
- **Defaults occupy ordinary slots; authoring the same slot replaces the
  default** — adopted from eve. Kit's core tools are the default tool set;
  the manifest can disable them; an authored tool with a default's name
  replaces it. One override rule, no configuration layers.

## 4. The manifest

### Formats

The manifest is **`agent.yaml` by default. `agent.toml` and `agent.json` are
accepted.** All three parse into one schema through one loader.

| Format | File | Why |
|---|---|---|
| YAML | `agent.yaml`, `agent.yml` | primary. Hand-edited config wants comments. It is the convention this repo already uses (`.golangci.yml`, `goreleaser.yaml`). |
| TOML | `agent.toml` | accepted. Same properties; some operators prefer it. |
| JSON | `agent.json` | accepted for tooling. No comments, so never the recommended form. |

Dependency note: `gopkg.in/yaml.v3` and `github.com/pelletier/go-toml/v2`
are already in the module graph as Kit's transitive dependencies. L2
promotes them to direct imports. **No new `go.sum` entries.** Both are pure
Go. The static binary is unchanged. `fsnotify` (for `bonnie dev`) is
promoted the same way.

### Discovery and ambiguity

`serve --agent DIR` and `build` look for `agent.yaml`, `agent.yml`,
`agent.toml`, `agent.json` in DIR, in that order. **More than one present is
an error** naming every path found — a silently preferred file hides
mistakes. `--config PATH` names one explicitly and skips discovery.

### Strictness

The loader is strict, and the strictness lives in the loader, not in three
decoders:

- An **unknown key is an error** that names the key. A typo that falls back
  to a default is the same failure class as the network-policy bug in
  SPEC §4.11: success for a control nothing applied.
- **`apiVersion` is required** and checked. Unknown version, error.
- Implementation: decode into the struct and into a generic key map, then
  diff the key sets. One code path, three formats, uniform errors.

### Schema `bonnie.dev/v0alpha`

```yaml
apiVersion: bonnie.dev/v0alpha
title: deploy-bot
model: anthropic/claude-sonnet-4-5     # optional; Kit default when absent
instructions: instructions.md          # optional; this default
sandbox:
  kind: docker                         # none | docker | microsandbox | local | auto
  image: python:3.12-slim              # optional
  network: allow-all                   # allow-all | deny-all
channels:
  http:
    addr: ":8080"
skills: skills/                        # optional directory
workspace: workspace/                  # optional directory
```

- `network` maps onto the sandbox backends' real policies. Docker enforces
  `deny-all` and `allow-all`; microsandbox additionally enforces a host
  allow-list. A mode a backend cannot enforce is an error, per invariant 10.
- `kind: none` gets the same loud warning `bonnie serve` prints today — the
  manifest must not make "no isolation" quieter than the flag does.
- **Precedence: flags over manifest over defaults.** The `serve` banner
  prints each setting with its source (`flag`, `agent.yaml`, `default`),
  extending the existing sandbox banner ethic.
- **No `auth` key.** The HTTP channel carries a `Principal` and does not
  verify one (README limits). A manifest key that promises authentication
  the channel does not perform is exactly the failure SECURITY.md exists to
  prevent. Add the key only with the verification.
- **MCP connections are reserved, not specified.** Kit's kernel includes
  MCP; the wiring options exist upstream. The field name is reserved in
  `v0alpha` and refuses with a clear error until the Kit API surface is
  verified and the schema for it is written. Do not ship a guess.

## 5. The codegen contract

- **Input:** `tools/<name>/tool.go` directories. Each must export
  `func Tool() kit.Tool`. The tool name is the directory name.
- **Output:** `bonnie_gen.go` at the module root. It imports each tool
  package, calls `Tool()`, and hands the set to the runner wiring.
- **Duplicate tool names are a generator error** before the build, and a
  compile error as backstop. Discovery failures are build failures — the
  Go-native kind, with a file and a line.
- **Idempotent.** Two runs produce byte-identical output. Guard test below.
- **Authored files are never rewritten.** `instructions.md`, `tools/`,
  `skills/`, `workspace/`, `main.go` belong to the user. Only
  `bonnie_gen.go` is generated; it carries a DO-NOT-EDIT banner and is safe
  to delete.
- **The import allowlist.** The generator emits only: standard library,
  `github.com/mark3labs/bonnie/...` public packages, and
  `github.com/mark3labs/kit/pkg/kit`. Anything else is a generator error.
  The boundary rule (SPEC §2) applies to generated code too, and the
  generator cannot emit a violation.
- Custom hooks that mutate are a **later** extension of the same contract
  (`func Hook() ...`); they are not in `v0.2`.

## 6. The commands

### `bonnie init`

- Default scaffold: `agent.yaml`, `instructions.md`, `skills/`,
  `workspace/`. No Go module — the zero-Go path is the default.
- `--tools` adds `go.mod`, `main.go` (calls the generated wiring), and one
  sample tool. `go build ./...` passes on the fresh scaffold.
- `--format yaml|toml|json` picks the manifest form. Default YAML.
- **Never overwrites an existing file.** It refuses and names the file.
  `--force` does not exist in `v0.2`.

### `bonnie serve --agent DIR`

- Reads the manifest, loads instructions from disk, wires channels and
  sandbox, serves. **This is real run-time discovery, and it needs no Go
  toolchain on the host.**
- A tree containing `tools/` or a `go.mod` cannot be honored by the generic
  binary. `serve` **refuses** with an error that says so and names
  `bonnie build`. Refusing is not failing; silently skipping the user's
  tools is the failure (invariant 13 below).
- Existing `serve` flags (`--model`, `--system-prompt`, `--sandbox`,
  `--journal`, `--addr`) override the manifest, and the banner says which
  source won.

### `bonnie dev`

- The loop: watch the tree → regenerate (`bonnie_gen.go`, when the tree has
  tools) → `go build` (when there is a module) → restart the child `serve`.
- Watch set: the manifest, instructions, `skills/`, `workspace/`,
  `tools/**`, `go.mod`, `go.sum`. Watcher: `fsnotify` (already in the
  graph). Debounce; details to the task.
- Restart is graceful: SIGTERM the child, wait out its drain
  (`--shutdown-timeout`), then start the next. Why restarts are safe — this
  is the part post-MVP work paid for:
  - a parked run holds no compute and lives in the journal;
  - a killed turn keeps its finished steps (SPEC §3.3) and `Start`
    continues it;
  - a stream client reconnects with `?cursor=` and the journal replays the
    gap (T-016, `Runner.StreamEvents`).
- This is eve's `npm run dev` with a compile in the middle. The cost is
  seconds per save on a small module, not milliseconds. That is the honest
  price of Go, and it buys a real artifact.

### `bonnie build`

- Codegen (if needed), embed `instructions.md`, `skills/`, `workspace/` via
  `go:embed` into the generated file, `go build`. Output:
  `./<title>` — one static binary.
- **The build machine needs Go. The host needs nothing** — no BONNIE CLI,
  no `--agent` flag, no runtime. The embedded agent serves from the binary.
- This is the deployment story eve cannot match: an eve agent is
  interpreted by the eve runtime forever; a BONNIE agent graduates into its
  own binary. Deployment documentation states the rest plainly: copy and
  run, one owner per run per host (SPEC §4.7), authenticate in front of the
  channel.
- `--dry-run` prints the discovery plan: the files found, the tools
  generated, the embed set. This is the `eve info` analogue and the
  debugging tool for "why did my tool not load?"

## 7. What we take from eve, decision by decision

Source: [getting-started](https://eve.dev/docs/getting-started) and the pages
linked from it, plus the analogues table in SPEC §7.

### Adopted

| eve decision | BONNIE form |
|---|---|
| Naming from paths | directory name is the tool name; no separate registration |
| Defaults occupy ordinary slots; authoring replaces | Kit core tools are defaults; the manifest or an authored tool overrides |
| `instructions.md` is the one required file | same, loaded from disk by `serve --agent`, embedded by `build` |
| Skills are flat markdown | same; embedded and seeded at sandbox open |
| Evals live beside the tree, not inside it | `bonnie eval` (T-019) reads the same tree |
| `eve info` for discovery debugging | `--dry-run` on `build` and `dev` |
| The dev loop as the primary inner experience | `bonnie dev`, with a compile in the middle |

### Adapted

| eve | eve's way | BONNIE's way | Why the flip |
|---|---|---|---|
| Dev loop | transpile, hot reload, milliseconds | regen + compile + restart, seconds | Go compiles; the artifact is a binary |
| Deployment | push to Vercel; the runtime hosts you | `bonnie build`; copy the binary anywhere | no Node, no account, no vendor; journal and sandbox run on the operator's hardware |
| Connections | `connections/` TS files for MCP and OpenAPI | manifest field, MCP first | MCP is config-shaped (a URL and options), so the manifest carries it; OpenAPI needs a generator — later |
| Sandbox | framework-provided | operator's choice of backend, from the manifest | runs on your hardware; a policy the backend cannot enforce is refused, not pretended (SPEC §4.11) |
| Channels | `channels/` TS entry points | `channels:` in the manifest; adapters in Go joined via `channeltest` (T-015) | interface already exists; the manifest binds, it does not implement |

### Refused

| eve feature | Why not |
|---|---|
| Run-time file discovery as the loading mechanism | Go compiles; codegen is the mechanism (§5) |
| Frontend frameworks / playground | no web client ships in BONNIE (SPEC §5 scope). The NDJSON stream with a cursor is the browser integration surface |
| `instrumentation.ts` (OTel) | out of MVP scope (SPEC §5); revisit at L4 |
| Schedules (`schedules/`) | needs a daemon story; `serve` is the future host — a later L2 increment, not `v0.2` |
| Subagents (`subagents/`) | out of MVP scope (SPEC §5); the tree schema does not preclude it |
| A browser chat UI in the repo | same scope decision |

## 8. The graduation path

The business logic in one view. Each step is a smaller leap than the last,
and the first three need no Go:

```
1. bonnie init                    five minutes to a running agent (no Go)
2. edit instructions.md           the agent is yours (still no Go)
3. agent.yaml: sandbox, channels  isolation and transports (still no Go)
4. skills/, workspace/            procedures and seed files    (still no Go)
5. bonnie init --tools            real tools, real Go, typed
6. bonnie build                   your own single static binary
```

eve offers the same arc with Node and ends on Vercel's runtime.
BONNIE's arc ends on a binary the user owns. Every step after 5 keeps
compiling, so nothing the user wrote ever stops being theirs.

## 9. New invariants

These extend SPEC §8 and need the guard tests in §10.

11. **Generated code uses the public surface only.** The generator's import
    allowlist is: standard library, BONNIE public packages,
    `kit/pkg/kit`. No `kit/internal`, no fantasy, ever.
12. **Generated files are disposable; authored files are sacred.**
    Regeneration is idempotent. The tool never rewrites a file the user
    owns. `init` never overwrites.
13. **Discovery refuses what it cannot fully honor.** `serve --agent` on a
    tree with Go tools is an error naming `bonnie build`, not a partial
    run. The same refusal ethic as invariant 10, applied to loading.
14. **The manifest is strict.** Unknown key, unknown `apiVersion`, two
    manifests in one root — all errors that name what is wrong.

## 10. Guard tests

- Codegen run twice over the same tree produces byte-identical output.
- A duplicate tool name fails the generator with both paths named.
- The loader rejects an unknown key, naming it, in all three formats.
- The loader rejects an `apiVersion` it does not know.
- Two manifests in one root is an error naming both files.
- `init` into a directory with an existing `instructions.md` fails and does
  not touch it.
- `serve --agent` on a data-only tree serves; the same tree with `tools/`
  added refuses with the `bonnie build` message.
- `serve --agent` with `kind: none` prints the no-isolation warning.
- **The dev-restart test** — a run parks in the child process, `bonnie dev`
  restarts it, a respond in the new child completes the run. This crosses a
  process boundary in spirit, per AGENTS.md, and is invariant 4 wearing
  dev-loop clothes.
- The generated file's imports, grepped against the allowlist.

## 12. Open questions

- **Declarative exec tools.** A manifest tool that runs a fixed command in
  the configured sandbox — zero Go, high value. The rule is already fixed:
  one requires `sandbox.kind != none`, or the manifest is refused (a
  manifest-only host must not gain a shell as its own process). The args
  schema is open. Candidate for `v0.3`.
- **Many agents per repository.** `v0.2` is one agent per root. Subagents
  and monorepos revisit this.
- **Embed versus disk for `serve --agent`.** Disk is the point (no build).
  A `--embed` flag on serve would blur the two modes; do not add it without
  a use case.
- **Windows file watching.** `fsnotify` covers it unevenly; `dev` degrades
  to polling there if needed. Not a blocker.
- **Dynamic instructions.** eve composes static sources at build time and
  resolves dynamic ones at run time. BONNIE `v0.2` is static-only; a Go
  hook returning the prompt is the later shape.
