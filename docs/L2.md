# BONNIE L2 Specification — Discovery: the agent tree

**Status:** T-017 shipped (`init`, `serve`, workspace seeding); T-018 shipped
(codegen, `bonnie dev`, `bonnie build`); T-024 shipped (the manifest was
removed — configuration is code) — the remaining L2 work is T-019 (evals) ·
**Audience:** implementing agent · **Read first:** [`SPEC.md`](SPEC.md)
(especially §1 layers, §8 invariants)

This document specifies the layer that turns BONNIE from a library you wire
by hand into a framework you scaffold, edit, and build. It records what is
adopted from eve's authoring model, what is adapted for Go, and what is
refused on purpose.

---

## 1. What L2 is

L1 made a run durable. L3 made it reachable. L2 makes an agent **authored**:
a directory of files with meaning from their paths, which BONNIE discovers,
wires, and compiles.

```
authored tree          discovery                    one static binary
─────────────         ──────────                    ─────────────────
main.go         ──┐    one call → bonnie.Main   ┌→   bonnie dev   (hot reload)
instructions.md   │  ┌───────────────────────┤
skills/           ├──┤ codegen   → build time  │→   bonnie build → ./my-agent
workspace/        │  └───────────────────────┤
tools/*/tool.go ─┘         go build         ┘    the binary alone serves
```

The central fact, restated from the design discussion: **discovery is a
build-time idea in Go.** eve discovers at run time because Node loads
TypeScript on every start. Go compiles. So the tree's data resolves from
fixed paths (read from disk while developing, embedded into the binary at
build), code resolves at build time, and the binary is the product of
discovery — not the thing that rules it out.

### The one rule

**No run-time plugin loading.** No `.so` plugins, no reflection registries,
no embedded interpreter. Go's `plugin` package is platform-fragile and would
break the single-static-binary property. Code is wired by codegen; data is
read from the paths §3 fixes. Say this in every task that touches L2, or a
contributor will reach for `dlopen`.

---

## 2. The two kinds

| Kind | Examples | Resolves | Mechanism |
|---|---|---|---|
| **Data** | instructions, skills, workspace seed files | run time from a fixed path, or build time via `go:embed` | the default layout (§3) |
| **Code** | the model, the sandbox, channels, custom tools, mutating hooks | build time only | options on `bonnie.Main`, and codegen into `bonnie_gen.go` |

The split answers "what is there to discover in a compiled binary?":
everything data-shaped is discovered when the process reads its tree or when
`build` embeds it; everything code-shaped is discovered when the generator
walks the tree and the compiler type-checks the result.

**There is no manifest.** A setting that is not a file is a Go call, so a
setting that does not exist is a compile error rather than a key nothing
reads. This is eve's decision (`defineAgent` in `agent.ts`), reached the long
way: `v0.2` shipped a strict `agent.yaml` and `v0.3` removed it. What the
manifest bought — a host with no Go toolchain serving a tree from data — was
not worth two places for one setting to live. See §7 and T-024.

## 3. The tree

```
my-agent/
├── main.go               # one call: bonnie.Main(...) — authored, never rewritten
├── instructions.md       # base system prompt — the one required data file
├── go.mod                # every tree is a Go module
├── tools/                # optional Go tools, one directory per tool
│   └── charge_card/
│       └── tool.go       # func Tool() kit.Tool
├── skills/               # optional markdown; embedded (reserved: nothing loads it yet)
├── workspace/            # the agent's root for files; seeded into the sandbox
└── bonnie_gen.go         # generated; safe to delete and regenerate
```

The paths are constants in the root `bonnie` package —
`bonnie.DefaultInstructions`, `DefaultWorkspace`, `DefaultSkills`,
`DefaultJournal`, `DefaultAddr` — and every consumer reads them from there.
The scaffold, codegen, the dev loop's watch set, and the runtime cannot
disagree about where the workspace is, because the rule is written once.

Decisions:

- **The agent root is the module root** (eve's flat layout). A BONNIE agent
  project is a Go module; library-mode hosts that embed the runner in a
  larger application use none of this, and stay first-class. The scaffold
  does not create a nested `agent/` directory, because `go:embed` patterns
  cannot cross package boundaries and the generated file must be able to
  reach the authored files.
- **Naming from paths** — adopted from eve: `tools/charge_card/` names the
  tool `charge_card`; the agent is named by its module path's base name,
  which is the directory `bonnie init` was given (eve: `package.json` name,
  else directory name — [getting-started](https://eve.dev/docs/getting-started)).
- **Defaults occupy ordinary slots; authoring the same slot replaces the
  default** — adopted from eve. Kit's core tools are the default tool set; an
  authored tool with a default's name replaces it. One override rule, no
  configuration layers.

## 4. Configuration is code

The minimum a user writes is one call:

```go
package main

import "github.com/mark3labs/bonnie"

func main() { bonnie.Main() }
```

`bonnie.Main` parses the operator flags a serving binary accepts (`-addr`,
`-model`), then calls `bonnie.Run`, which reads `instructions.md`, roots the
agent's file tools in `workspace/`, opens the journal at `.bonnie`, mounts
the HTTP channel, and drains in-flight turns on a signal. Everything else is
an [`Option`]:

| Option | Replaces |
|---|---|
| `WithModel`, `WithKit` | the model and any Kit setting BONNIE does not name |
| `WithSystemPrompt`, `WithInstructions` | the prompt, or the file it is read from |
| `WithWorkspace`, `WithJournal`, `WithAddr` | the default paths and binding |
| `WithSandbox`, `WithNetwork` | tool isolation and its egress policy |
| `WithSlack`, `WithDiscord`, `WithTelegram`, `WithChannel` | the mounted transports |
| `WithTools` | tools added beside the discovered ones |
| `WithAgentFactory` | the agent itself, for a host that brings its own |

Rules:

- **Flags over options.** `-addr` and `-model` are applied last, so an
  operator can move a built binary to another port or model without
  rebuilding it. `bonnie dev` starts its child with `-addr`, and that is the
  whole contract between the loop and the child.
- **Secrets come from the environment, never from code.** Each chat channel
  fills its empty credential fields from its documented variables, and a
  missing one is a startup error naming the variable. A webhook that does not
  verify its caller is a door with no lock.
- **`kind: none` is still loud.** No sandbox is the default, and the startup
  warning is printed even when the banner is silenced.
- **No `auth` option.** The HTTP channel carries a `Principal` and does not
  verify one (README limits). An option that promises authentication the
  channel does not perform is exactly the failure SECURITY.md exists to
  prevent. Add the option only with the verification.
- **MCP is reserved, not specified.** Kit's kernel includes MCP; the wiring
  options exist upstream. No BONNIE option is offered until the Kit API
  surface is verified. Do not ship a guess.
- **An option that cannot apply is refused, not ignored.** A network policy
  without a sandbox, an image on a backend that runs none, and any agent
  option beside `WithAgentFactory` are startup errors naming both sides.

## 5. The codegen contract

- **Input:** `tools/<name>/tool.go` directories. Each must export
  `func Tool() kit.Tool`. The tool name is the directory name.
- **Output:** `bonnie_gen.go` at the module root. It imports each tool
  package, binds the embed slots, and calls `bonnie.Register` from `init`
  with the tools and the embedded instructions, skills, and workspace.
  Because it registers rather than declaring symbols `main.go` must call,
  adding a tool changes only the generated file.
- **`Registered` is a run-time read.** Go initialises package-level variables
  before it runs any `init`, so a host that wants the embedded data must ask
  for it inside `main`, not in a package-level `var`.
- **Duplicate tool names are a generator error** before the build, and a
  compile error as backstop. Discovery failures are build failures — the
  Go-native kind, with a file and a line.
- **Idempotent.** Two runs produce byte-identical output. Guard test below.
- **Authored files are never rewritten.** `main.go`, `instructions.md`,
  `tools/`, `skills/`, `workspace/` belong to the user. Only `bonnie_gen.go`
  is generated; it carries a DO-NOT-EDIT banner and is safe to delete.
- **The import allowlist.** The generator emits only: standard library,
  `github.com/mark3labs/bonnie` and its public packages, and
  `github.com/mark3labs/kit/pkg/kit`. Anything else is a generator error.
  The boundary rule (SPEC §2) applies to generated code too, and the
  generator cannot emit a violation.
- Custom hooks that mutate are a **later** extension of the same contract
  (`func Hook() ...`).

## 6. The commands

### `bonnie init`

- Scaffolds `main.go`, `instructions.md`, `go.mod`, `bonnie_gen.go`,
  `skills/`, `workspace/`. The fresh tree builds and serves unedited.
- `--tools` adds one sample tool, `tools/echo`.
- `--model` writes the `bonnie.WithModel` line into `main.go`.
- **Never overwrites an existing file.** It refuses and names every blocker.
  `--force` does not exist.

### `bonnie dev`

- The loop: watch the tree → regenerate `bonnie_gen.go` → `go build` →
  gracefully restart the child.
- Watch set: `main.go`, the instructions, `skills/`, `tools/**`, `go.mod`,
  `go.sum`. The workspace is **not** watched: it is where the running agent
  writes, so rebuilding on it would let the agent restart itself mid-turn.
- The child keeps its address across restarts, so a connected TUI survives
  one. Restart is graceful: SIGTERM, wait out the drain
  (`--shutdown-timeout`), then start the next. Why restarts are safe:
  - a parked run holds no compute and lives in the journal;
  - a killed turn keeps its finished steps (SPEC §3.3) and `Start`
    continues it;
  - a stream client reconnects with `?cursor=` and the journal replays the
    gap (T-016, `Runner.StreamEvents`).
- This is eve's `npm run dev` with a compile in the middle. The cost is
  seconds per save on a small module, not milliseconds. That is the honest
  price of Go, and it buys a real artifact.

### `bonnie build`

- Codegen, embed `instructions.md` (and `skills/`, `workspace/` when they
  hold real files) via `go:embed` into the generated file, `go build`.
  Output: `./<module>` — one static binary.
- **The build machine needs Go. The host needs nothing** — no BONNIE CLI, no
  runtime. The embedded agent serves from the binary alone.
- This is the deployment story eve cannot match: an eve agent is
  interpreted by the eve runtime forever; a BONNIE agent graduates into its
  own binary. Deployment documentation states the rest plainly: copy and
  run, one owner per run per host (SPEC §4.7), authenticate in front of the
  channel.
- `--dry-run` prints the discovery plan: the files found, the tools
  generated, the embed set. This is the `eve info` analogue and the
  debugging tool for "why did my tool not load?"

### `bonnie serve`

- The generic host: an agent configured entirely by flags, with no tree. It
  is what a user reaches for to try the runtime before authoring anything.
- It cannot serve a tree. A tree's configuration is Go in its own `main.go`,
  so the tree is served by running it — `bonnie dev` while working on it,
  `bonnie build` for the binary it graduates into.

## 7. What we take from eve, decision by decision

Source: [getting-started](https://eve.dev/docs/getting-started) and the pages
linked from it, plus the analogues table in SPEC §7.

### Adopted

| eve decision | BONNIE form |
|---|---|
| Configuration is code, not a config file | `main.go` options; `defineAgent` ↔ `bonnie.Main` |
| The config file is optional; framework defaults fill the slot | `bonnie.Main()` with no options is a working agent |
| Naming from paths | directory name is the tool name; no separate registration |
| Defaults occupy ordinary slots; authoring replaces | Kit core tools are defaults; an authored tool overrides |
| `instructions.md` is the one required file | same, from disk while developing, embedded by `build` |
| Skills are flat markdown | same; embedded (loading is reserved) |
| Evals live beside the tree, not inside it | `bonnie eval` (T-019) reads the same tree |
| `eve info` for discovery debugging | `--dry-run` on `build` and `dev` |
| The dev loop as the primary inner experience | `bonnie dev`, with a compile in the middle |

### Adapted

| eve | eve's way | BONNIE's way | Why the flip |
|---|---|---|---|
| Dev loop | transpile, hot reload, milliseconds | regen + compile + restart, seconds | Go compiles; the artifact is a binary |
| Deployment | push to Vercel; the runtime hosts you | `bonnie build`; copy the binary anywhere | no Node, no account, no vendor; journal and sandbox run on the operator's hardware |
| Sandbox | framework-provided | operator's choice of backend, from an option | runs on your hardware; a policy the backend cannot enforce is refused, not pretended (SPEC §4.11) |
| Channels | `channels/` TS entry points | adapters in Go, mounted by an option, joined via `channeltest` (T-015) | the interface already exists; the option binds, it does not implement |
| Connections | `connections/` TS files for MCP and OpenAPI | reserved | MCP needs its Kit surface verified; OpenAPI needs a generator |

### Refused

| eve feature | Why not |
|---|---|
| Run-time file discovery as the loading mechanism | Go compiles; codegen is the mechanism (§5) |
| Frontend frameworks / playground | no web client ships in BONNIE (SPEC §5 scope). The NDJSON stream with a cursor is the browser integration surface |
| `instrumentation.ts` (OTel) | out of MVP scope (SPEC §5); revisit at L4 |
| Schedules (`schedules/`) | needs a daemon story; a later L2 increment |
| Subagents (`subagents/`) | out of MVP scope (SPEC §5); the tree schema does not preclude it |
| A browser chat UI in the repo | same scope decision |

## 8. The graduation path

The business logic in one view. Each step is a smaller leap than the last:

```
1. bonnie init                    five minutes to a running agent
2. edit instructions.md           the agent is yours
3. main.go: WithModel, WithSandbox  the model and isolation
4. skills/, workspace/            procedures and seed files
5. tools/                         real tools, real Go, typed
6. bonnie build                   your own single static binary
```

eve offers the same arc with Node and ends on Vercel's runtime.
BONNIE's arc ends on a binary the user owns. Every step keeps compiling, so
nothing the user wrote ever stops being theirs.

The cost of removing the manifest is stated plainly: **Go is required on the
desk from step 1.** It was required from step 5 before. The host still needs
nothing, which is the end of the arc that matters.

## 9. New invariants

These extend SPEC §8 and need the guard tests in §10.

11. **Generated code uses the public surface only.** The generator's import
    allowlist is: standard library, BONNIE public packages,
    `kit/pkg/kit`. No `kit/internal`, no fantasy, ever.
12. **Generated files are disposable; authored files are sacred.**
    Regeneration is idempotent. The tool never rewrites a file the user
    owns. `init` never overwrites.
13. **Discovery refuses what it cannot fully honor.** A tool directory
    without `Tool()`, two tools declaring one name, an option that cannot
    apply beside another — all errors that name both sides, never a partial
    run. The same refusal ethic as invariant 10, applied to loading.
14. **There is one place to configure a setting.** A setting is a file at a
    fixed path or a Go option, never both, and never a third place that can
    disagree with the other two. The default paths are constants in the root
    package, read by every consumer.

## 10. Guard tests

- Codegen run twice over the same tree produces byte-identical output.
- A duplicate tool name fails the generator with both paths named.
- A tool directory without `func Tool()` fails, naming the directory.
- The generated file's imports, grepped against the allowlist.
- The generated file compiles, against this checkout.
- The scaffolded `main.go` is one call and wires no server by hand.
- The scaffold writes no manifest in any format.
- `init` into a directory with an existing `instructions.md` fails and does
  not touch it.
- The default paths are the scaffolded layout.
- A sandboxed agent receives no host tools; a sandboxed workspace becomes a
  seed.
- A network policy without a sandbox is refused; an agent option beside
  `WithAgentFactory` is refused, naming it.
- The system prompt falls back to the embedded copy, and a tree with neither
  file nor embed is refused.
- The workspace seed never overwrites an existing file.
- **The dev-restart test** — a run parks in the child process, `bonnie dev`
  restarts it, a respond in the new child completes the run. This crosses a
  process boundary in spirit, per AGENTS.md, and is invariant 4 wearing
  dev-loop clothes.
- **The graduation test** — `bonnie build`'s binary serves a full run from a
  directory with no tree beside it, answering from the embedded instructions.

## 12. Open questions

- **Slot-discovered sandbox and channels.** eve authors `agent/sandbox.ts`
  and `agent/channels/slack.ts` as files, and the framework wires them. The
  BONNIE equivalent is `sandbox/sandbox.go` exporting `func Sandbox()
  sandbox.Provider` and `channels/<name>/channel.go`, discovered by the same
  generator that walks `tools/` and registered the same way. It would make
  `main.go` stop growing for the two most common overrides. Candidate for
  `v0.4`; the `Register` seam was built so it is additive.
- **`sandbox/workspace/` instead of top-level `workspace/`.** eve nests the
  seed under the sandbox definition. BONNIE's workspace is also the host
  working directory when no sandbox is set, which eve has no analogue for, so
  the flat path stays until slot discovery lands.
- **Declarative exec tools.** A tool that runs a fixed command in the
  configured sandbox. The rule is already fixed: one requires a sandbox, or
  it is refused (a host must not gain a shell as its own process).
- **Template amortization for sandbox setup.** eve builds a sandbox
  definition's `bootstrap` hook (clone a baseline repo, install deps) once
  into a reusable template — a committed local Docker image or a backend
  snapshot — reused across sessions, invalidated by a `revalidationKey` and
  the tracked seed-file contents. The durability stance does not change: the
  template is a cache, the conversation stays the durable artifact, and a
  missing sandbox is noted and re-derived.
- **Many agents per repository.** One agent per root. Subagents and
  monorepos revisit this.
- **Windows file watching.** `fsnotify` covers it unevenly; `dev` degrades
  to polling there if needed. Not a blocker.
- **Dynamic instructions.** eve composes static sources at build time and
  resolves dynamic ones at run time. BONNIE is static-only; a Go hook
  returning the prompt is the later shape.
